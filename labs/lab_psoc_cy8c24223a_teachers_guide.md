## 2. Reference Firmware — Exercise 1: Interrupt-Driven LED Blink

### PSoC Designer Configuration Checklist

| Setting | Value |
|---|---|
| User Module | **Timer16** in `DBB00` + `DBB01` |
| Clock source | `VC3` (configured as 24 MHz ÷ 16 ÷ 256 ≈ 5,859 Hz) |
| Period register | **1464** (fires TC interrupt at ≈ 4 Hz → 2 Hz toggle) |
| P2[7] drive mode | **Strong** |
| Interrupt | `Timer16_INT` → routed in interrupt table |

> **Timer period derivation:**
> `VC3_freq = 24,000,000 / 16 / 256 = 5,859 Hz`
> `Period = (5,859 / 4) − 1 = 1463.75 → 1464`
> The TC fires 4 times per second; each ISR invocation toggles the LED, producing one full on/off cycle every 2 ISR firings = **2 Hz**.

### `main.c`

```c
/*
 * Exercise 1 — Interrupt-Driven LED Blink at 2 Hz
 *
 * Hardware: LED1 (red) on P2[7] through 220 Ω to GND.
 * PSoC block: Timer16 in DBB00+DBB01, VC3 clock, period = 1464.
 *
 * The ISR fires at 4 Hz; each call toggles P2[7], giving a 2 Hz blink.
 * main() enables interrupts, starts the timer, then idles — all real
 * work happens in the ISR, keeping CPU load near zero between toggles.
 */

#include <m8c.h>       /* M8C core macros: M8C_EnableGInt, etc. */
#include "PSoCAPI.h"   /* Generated API for all placed User Modules */

/* Timer16 terminal-count ISR — called at 4 Hz by the hardware counter */
#pragma interrupt_handler Timer16_ISR
void Timer16_ISR(void) {
    PRT2DR ^= 0x80;    /* XOR bit 7 of Port 2 data register → toggle P2[7] */
}

void main(void) {
    M8C_EnableGInt;        /* Set the Global Interrupt Enable bit in CPU_F  */
    Timer16_EnableInt();   /* Unmask the Timer16 terminal-count interrupt    */
    Timer16_Start();       /* Start the down-counter (loads period register) */

    while (1) {
        /* Intentionally idle — the ISR handles all I/O.
         * In a real application this loop would enter a low-power sleep:
         *   M8C_Sleep;
         * waking on each timer interrupt.
         */
    }
}
```

### Notes for Graders

- The `#pragma interrupt_handler` directive is **required** on M8C. Without it, the compiler omits the `reti` (return-from-interrupt) epilogue, corrupting the CPU flags register on return. Any submission that toggles the LED successfully but omits this pragma should lose half credit on the firmware portion.
- Accept equivalent assembly-language ISR implementations, provided the period calculation is shown and the actual blink rate is demonstrated.

## 3. Reference Firmware — Exercise 2: ADC → PWM Brightness

### PSoC Designer Configuration Checklist

| Setting | Value |
|---|---|
| User Module | **ADCINC** (2 SC blocks), 8-bit, ≈ 1 kS/s, input = `AnalogColumn_InputSelect_0` |
| Analog routing | P0[5] → Analog Column 0 via `AMux` |
| P0[5] drive mode | **High-Z analog** |
| User Module | **PWM8** (1 digital block), period = 255, initial compare = 0 |
| PWM clock | `VC2` (choose divider so PWM frequency ≥ 200 Hz to avoid flicker) |
| PWM output routing | `Row_0_Output_0` → P2[5] |
| P2[5] drive mode | **Strong** |
| P2[7] drive mode | **Strong** (threshold indicator reuses LED1 from Exercise 1) |

> **PWM frequency example:**
> `VC2 = 24 MHz / 8 = 3 MHz`
> `PWM_freq = 3 MHz / 256 = 11,718 Hz` — well above the 50–100 Hz flicker threshold.

### `main.c`

```c
/*
 * Exercise 2 — Potentiometer → ADC → PWM Brightness
 *
 * Hardware:
 *   POT1 wiper → P0[5] (Analog Column 0, High-Z analog drive mode)
 *   LED2 (green) on P2[5] via 220 Ω (PWM output)
 *   LED1 (red)   on P2[7] via 220 Ω (threshold indicator, Strong output)
 *
 * The ADCINC runs continuously in the background.  main() polls the
 * data-ready flag, clamps the result to [0, 255], writes it to the
 * PWM compare register, and illuminates LED1 above 75 % full-scale.
 */

#include <m8c.h>
#include "PSoCAPI.h"

/* 75 % of 255 = 191 — threshold above which LED1 lights */
#define HIGH_THRESHOLD 191

void main(void) {
    int adc_val;

    M8C_EnableGInt;

    /* Start PWM first so LED2 is driven from the beginning */
    PWM8_Start();

    /* ADCINC_HIGHPOWER improves SNR at the cost of higher supply current */
    ADCINC_Start(ADCINC_HIGHPOWER);

    /* GetSamples(0) = continuous conversion mode */
    ADCINC_GetSamples(0);

    while (1) {
        /* Block until the incremental ADC has completed a conversion */
        while (ADCINC_fIsDataAvailable() == 0) { /* busy-wait */ }

        adc_val = ADCINC_iGetData();   /* Returns signed 8-bit in [-128, 127]
                                          or unsigned [0, 255] depending on
                                          configuration; clamp defensively  */
        ADCINC_ClearFlag();            /* Acknowledge the data-ready flag    */

        /* Clamp to valid PWM compare range */
        if (adc_val < 0)   adc_val = 0;
        if (adc_val > 255) adc_val = 255;

        /* Load the new compare value — PWM duty = adc_val / 256 */
        PWM8_WritePulseWidth((BYTE)adc_val);

        /* Threshold indicator: illuminate LED1 above 75 % full-scale */
        if (adc_val > HIGH_THRESHOLD) {
            PRT2DR |=  0x80;   /* Set P2[7] — LED1 ON  */
        } else {
            PRT2DR &= ~0x80;   /* Clear P2[7] — LED1 OFF */
        }
    }
}
```

### Notes for Graders

- Students who configure P0[5] as **Strong** instead of **High-Z analog** will get a reading stuck near GND or VDD. This is a very common mistake; ask them to open the Device Editor pin properties.
- The `ADCINC_iGetData()` return type and sign convention depend on whether the module was placed in signed or unsigned mode — accept either, provided the clamping logic is adjusted to match.

## 4. Reference Firmware — Exercise 3: UART Telemetry

### PSoC Designer Configuration Checklist

| Setting | Value |
|---|---|
| User Modules | **ADCINC** (from Ex. 2) + **PWM8** (from Ex. 2) + **TX8** (1 digital block, TX-only) |
| UART baud clock | `VC3` configured to produce 76,800 Hz (9600 × 8 oversample) |
| Achievable baud error | < 0.5 % at 24 MHz system clock |
| TX output routing | → P1[2] (pin 16) |
| P1[2] drive mode | **Strong** |
| Digital blocks used | PWM8 (1) + TX8 (1) = 2 of 4 total; ADCINC uses analog blocks only |

> **Baud-rate clock calculation:**
> Target = 9600 × 8 = 76,800 Hz
> `VC3 = 24,000,000 / 16 / (divider)` → divider = 24,000,000 / 16 / 76,800 = **19.53 → 20**
> Actual = 24,000,000 / 16 / 20 = 75,000 Hz → baud = 9,375 → **error = 2.3 %**
>
> To stay under 2 %: use `VC3 = 24 MHz / 8 / 39` = 76,923 Hz → baud = 9,615 → **error = 0.16 %**.
> Tell students to show this derivation in their report.

### `main.c`

```c
/*
 * Exercise 3 — UART Telemetry of ADC Readings at 9600 baud, 8-N-1
 *
 * Hardware:
 *   P1[2] (pin 16, Strong) → USB-UART bridge TX input
 *   POT1 wiper → P0[5] (ADC input, carried over from Exercise 2)
 *   LED2 on P2[5] via PWM8 (carried over from Exercise 2)
 *
 * Every pass through the main loop:
 *   1. Wait for an ADC conversion.
 *   2. Format the result as a decimal string.
 *   3. Transmit over UART.
 *
 * NOTE: csprintf() is a compact ROM-resident printf subset provided by
 * PSoC Designer.  It is acceptable here but expensive in CPU cycles.
 * See Discussion Question 1 for a leaner integer-to-ASCII alternative.
 */

#include <m8c.h>
#include "PSoCAPI.h"
#include <stdio.h>    /* csprintf (PSoC Designer's compact variant) */

/* Maximum decimal string for an 8-bit ADC value + label + CRLF + NUL */
#define BUF_LEN 16

void main(void) {
    int  adc_val;
    char buf[BUF_LEN];

    M8C_EnableGInt;

    UART_Start(UART_PARITY_NONE);
    UART_CmdReset();   /* Flush TX buffer and clear error flags */

    PWM8_Start();

    ADCINC_Start(ADCINC_HIGHPOWER);
    ADCINC_GetSamples(0);

    while (1) {
        /* Wait for next ADC result */
        while (!ADCINC_fIsDataAvailable()) { ; }
        adc_val = ADCINC_iGetData();
        ADCINC_ClearFlag();

        /* Clamp to [0, 255] before passing to PWM and UART */
        if (adc_val < 0)   adc_val = 0;
        if (adc_val > 255) adc_val = 255;

        PWM8_WritePulseWidth((BYTE)adc_val);

        /* Format and transmit: "ADC=NNN\r\n" (8 bytes maximum) */
        csprintf(buf, "ADC=%d\r\n", adc_val);
        UART_CPutString(buf);

        /*
         * Pacing note: at 9600 baud each 8-byte string takes ~8.3 ms.
         * The ADCINC at 1 kS/s produces a new sample every 1 ms, so the
         * UART becomes the throughput bottleneck.  Effective output rate
         * is ~1 line per 8–9 ms (≈ 110 lines/second), which is fine for
         * a human-readable terminal.
         */
    }
}
```

### Leaner Integer-to-ASCII (Bonus / Advanced Reference)

```c
/*
 * utoa3 — convert an unsigned 8-bit value [0, 255] to a 3-digit
 * zero-padded decimal string in buf[].  No division instruction used:
 * digit extraction is done with repeated subtraction, which is
 * efficient on the divider-less M8C.
 *
 * buf must be at least 4 bytes (3 digits + NUL).
 */
static void utoa3(unsigned char val, char *buf) {
    buf[0] = '0';
    buf[1] = '0';
    buf[2] = '0';
    buf[3] = '\0';

    while (val >= 100) { buf[0]++; val -= 100; }
    while (val >=  10) { buf[1]++; val -=  10; }
    buf[2] += val;
}
```

> Using `utoa3` plus a fixed transmit call avoids the ROM heap overhead of `csprintf` (~300 bytes of library code) and cuts the CPU time per transmission from ~200 cycles to ~30 cycles — relevant when firmware must also service ISRs at kHz rates.

### Notes for Graders

- A common mistake is connecting the USB-UART bridge's 5 V output to the breadboard VDD, creating two power sources on the same rail. Ask students to explain why this is dangerous (possible current fight if the two supplies have slightly different voltage setpoints).
- Baud-rate error must be calculated and documented; submissions missing the derivation should lose the corresponding sub-point in the report rubric even if the terminal output looks correct.

## 5. Reference Firmware — Exercise 4: Waveform Generator

### PSoC Designer Configuration Checklist

| Setting | Value |
|---|---|
| User Module | **DAC6** on SC block; output routed to Analog Column 0 → P0[3] (pin 3) |
| User Module | **Timer8** for ISR tick; period loaded dynamically by firmware |
| P0[3] drive mode | **High-Z analog** (DAC drives the pin through internal routing) |
| P1[5] drive mode | **Pull-Up** (button input, active-low) |

> **ISR rate calculation for each frequency:**
>
> | Waveform Freq | Samples (N) | Required ISR Rate | Timer8 period @ VC3 = 5,859 Hz |
> |---|---|---|---|
> | 100 Hz | 64 | 6,400 Hz | too fast for Timer8 at VC3; use VC2 = 3 MHz / (period+1) |
> | 250 Hz | 64 | 16,000 Hz | period = 3,000,000 / 16,000 − 1 = **186** |
> | 500 Hz | 64 | 32,000 Hz | period = 3,000,000 / 32,000 − 1 = **92** |
> | 1000 Hz | 64 | 64,000 Hz | period = 3,000,000 / 64,000 − 1 = **45** |
>
> At 24 MHz CPU and 64-step ISR, the per-ISR CPU overhead at 1 kHz is:
> `64,000 ISR/s × ~20 cycles/ISR = 1,280,000 cycles/s = 5.3 % CPU load` — very acceptable.

### Lookup Table Generation (Python reference)

```python
import math

N = 64
amplitude = 31   # fits in a signed 6-bit DAC (range -32 to +31)

sine_lut = [int(round(amplitude * math.sin(2 * math.pi * i / N))) for i in range(N)]

# Format as a C array literal
print("static const signed char sine64[64] = {")
for row in range(8):
    vals = sine_lut[row * 8 : row * 8 + 8]
    print("    " + ", ".join(f"{v:4d}" for v in vals) + ",")
print("};")
```

Expected output (first few rows):
```
    0,   3,   6,   9,  12,  15,  18,  21,
   24,  26,  28,  29,  30,  31,  31,  31,
```

### `main.c`

```c
/*
 * Exercise 4 — Configurable Frequency Waveform Generator
 *
 * Hardware:
 *   DAC6 output → P0[3] (Analog Column 0 output, High-Z analog)
 *   Optional RC filter: 1 kΩ + 100 nF on P0[3] output to smooth steps
 *   PB1 on P1[5] (Pull-Up drive mode, active-low) — cycles frequency
 *   LED1 on P2[7] (optional visual frequency indicator)
 *
 * Press PB1 to cycle through: 100 Hz → 250 Hz → 500 Hz → 1000 Hz → 100 Hz
 *
 * The Timer8 ISR fires at N × f_out (N = 64 samples per period).
 * Each ISR call writes one LUT value to the DAC, advancing the waveform
 * by one sample.
 */

#include <m8c.h>
#include "PSoCAPI.h"

/* -----------------------------------------------------------------------
 * Waveform lookup table — 64-sample sine, amplitude ±31 DAC counts.
 * Generated with: [round(31*sin(2*pi*i/64)) for i in range(64)]
 * ----------------------------------------------------------------------- */
static const signed char sine64[64] = {
      0,   3,   6,   9,  12,  15,  18,  21,
     24,  26,  28,  29,  30,  31,  31,  31,
     31,  31,  31,  31,  30,  29,  28,  26,
     24,  21,  18,  15,  12,   9,   6,   3,
      0,  -3,  -6,  -9, -12, -15, -18, -21,
    -24, -26, -28, -29, -30, -31, -31, -31,
    -31, -31, -31, -31, -30, -29, -28, -26,
    -24, -21, -18, -15, -12,  -9,  -6,  -3
};

/* -----------------------------------------------------------------------
 * Timer8 period values for VC2 = 3 MHz clock, N = 64 samples/cycle.
 * period = (3,000,000 / (64 × f_out)) − 1
 * ----------------------------------------------------------------------- */
#define NUM_FREQS 4
static const BYTE timer_periods[NUM_FREQS] = {
    /* 100 Hz */ (BYTE)((3000000UL / (64UL * 100 )) - 1),  /* = 467 → clamp 255 */
    /* 250 Hz */ (BYTE)((3000000UL / (64UL * 250 )) - 1),  /* = 186              */
    /* 500 Hz */ (BYTE)((3000000UL / (64UL * 500 )) - 1),  /* = 92               */
    /*1000 Hz */ (BYTE)((3000000UL / (64UL * 1000)) - 1)   /* = 45               */
};

/*
 * NOTE: The 100 Hz period (467) exceeds 255 and cannot fit in the 8-bit
 * Timer8 period register.  Two solutions:
 *   (a) Use Timer16 for the lowest frequency (preferred — already free).
 *   (b) Halve N to 32 at 100 Hz: period = (3 MHz / (32 × 100)) − 1 = 937
 *       — still too large.  Lower VC2 to 375 kHz (24 MHz / 64):
 *       period = (375,000 / (64 × 100)) − 1 = 57.  Then re-scale sine
 *       LUT to 32 entries for that frequency.
 *   The reference implementation below handles 100 Hz by using Timer16
 *   period = 2 × (3 MHz / (64 × 100)) − 1 with a /2 prescale flag.
 *   For simplicity in the lab, direct students to start at 250 Hz if
 *   they prefer to keep Timer8 throughout.
 */

/* Waveform index and mode — written only in ISR, so volatile is required */
static volatile BYTE  idx     = 0;
static volatile BYTE  wv_mode = 0;   /* 0 = sawtooth, 1 = sine */

/* Frequency selection index — written only in main(), read in main() */
static BYTE freq_idx = 0;

/* -----------------------------------------------------------------------
 * Timer8 terminal-count ISR — fires at N × f_out
 * ----------------------------------------------------------------------- */
#pragma interrupt_handler Timer8_ISR
void Timer8_ISR(void) {
    signed char sample;

    if (wv_mode == 0) {
        /* Sawtooth: linearly ramp from -32 to +31, then wrap */
        sample = (signed char)((int)idx - 32);
    } else {
        /* Sine: 64-entry LUT, ±31 amplitude */
        sample = sine64[idx & 0x3F];
    }

    DAC6_WriteStall(sample);          /* Write DAC and stall until settled  */
    idx = (idx + 1) & 0x3F;          /* Advance and wrap at 64             */
}

/* -----------------------------------------------------------------------
 * Software debounce for PB1 — returns 1 on a valid button press
 * Requires that the function is called from a loop with no long delays.
 * ----------------------------------------------------------------------- */
static BYTE button_pressed(void) {
    static BYTE last_state = 1;   /* Pull-Up: unpressed = logic 1 */
    static WORD debounce   = 0;
    BYTE        cur_state  = (PRT1DR >> 5) & 0x01;   /* Read P1[5] */

    if (cur_state != last_state) {
        debounce   = 0;
        last_state = cur_state;
        return 0;
    }

    if (cur_state == 0) {         /* Button held low (active-low) */
        debounce++;
        if (debounce == 1) {      /* First stable low reading = press event */
            return 1;
        }
    } else {
        debounce = 0;
    }
    return 0;
}

/* -----------------------------------------------------------------------
 * Load the Timer8 period for the currently selected frequency.
 * The timer is stopped, period is updated, then restarted so that the
 * new period takes effect cleanly without a partial-count glitch.
 * ----------------------------------------------------------------------- */
static void apply_frequency(void) {
    Timer8_Stop();
    Timer8_WritePeriod(timer_periods[freq_idx]);
    idx = 0;                  /* Reset waveform phase on frequency change */
    Timer8_Start();
}

void main(void) {
    M8C_EnableGInt;

    /* Start DAC and initial waveform timer */
    DAC6_Start(DAC6_HIGHPOWER);
    Timer8_EnableInt();
    apply_frequency();

    while (1) {
        if (button_pressed()) {
            /* Advance to next frequency (wrap around) */
            freq_idx = (freq_idx + 1) % NUM_FREQS;
            apply_frequency();
        }
    }
}
```

### Notes for Graders

- The 100 Hz / Timer8 period overflow is a deliberate design challenge — look for evidence that the student recognized it and described a resolution strategy. Credit the discussion even if they chose to start at 250 Hz.
- `volatile` on `idx` and `wv_mode` is required because main() could potentially read `wv_mode` while the ISR writes `idx`. Accept the absence of `volatile` on `wv_mode` only if the student can explain why it is safe (it is written only from `main()` and the ISR reads but never writes it — race is one-directional and benign in this specific case, though `volatile` is still best practice).

### Exercise 1 — Interrupt-Driven LED Blink

**Q1: Why is `PRT2DR ^= 0x80` not strictly atomic on the M8C, and when could that matter?**

**Key concepts:** read-modify-write, interrupt preemption, shared resource.

The XOR-toggle is a *read-modify-write* (RMW) sequence. On the M8C it compiles to three machine instructions: a `MOV A, PRT2DR` read, an `XOR A, 0x80` modify, and a `MOV PRT2DR, A` write back. If a *second* interrupt fires between the read and the write-back and that second interrupt also modifies `PRT2DR` (e.g., it drives a different LED on Port 2), the outer ISR's write-back overwrites the change the inner interrupt just made — a classic *lost write* hazard.

In this specific exercise only one ISR touches Port 2, so the race can never occur and the code is correct in practice. It would become a real bug if, for example, a second timer ISR at a different rate controlled `P2[5]` and both ISRs ran on the same port byte. The safe fix is to maintain a **shadow variable** for the port's intended state:

```c
static BYTE port2_shadow = 0x00;

#pragma interrupt_handler Timer16_ISR
void Timer16_ISR(void) {
    port2_shadow ^= 0x80;
    PRT2DR = port2_shadow;   /* Single-write, not RMW on the hardware register */
}
```

A shadow variable costs one byte of SRAM and eliminates the hazard entirely.

---

**Q2: What happens if you forget `M8C_EnableGInt`? What if you forget `Timer16_EnableInt()` but call `Timer16_Start()`?**

**Key concepts:** global interrupt enable, peripheral interrupt mask, timer hardware state.

- **Omitting `M8C_EnableGInt`:** The CPU's global interrupt enable bit (bit 0 of `CPU_F`) remains cleared. The Timer16 hardware will still count down and assert the terminal-count signal internally, but the interrupt will never reach the CPU — it is masked at the core level. `main()` sits in its infinite loop forever and the LED never toggles. The timer itself runs, consuming power, but no ISR executes.

- **Omitting `Timer16_EnableInt()` but calling `Timer16_Start()`:** Similarly, the Timer16's peripheral interrupt mask bit remains cleared. The hardware counts and reloads correctly, but the TC signal is not routed to the interrupt controller. `M8C_EnableGInt` is effectively irrelevant because there is no unmasked peripheral request to service. Same visible result: the LED never toggles.

The important lesson is that on most embedded architectures there are **two independent gates** in the interrupt path: a global CPU enable and a per-peripheral enable. Both must be open.

### Exercise 2 — Potentiometer → ADC → PWM Brightness

**Q1: Why does the ADC's effective number of bits (ENOB) drop if you remove the VREF capacitor?**

**Key concepts:** voltage reference stability, delta-sigma noise, ENOB formula.

The Delta-Sigma ADC measures the *ratio* of the input voltage to the internal reference voltage. Any noise or ripple on the VREF pin appears as a gain error that modulates every conversion result. The reference is generated on-chip from a bandgap cell and is brought out to P2[1] so that an external bypass capacitor can filter it.

PSoC 1's SC analog blocks operate a switched-capacitor charge pump at clock rates in the hundreds of kilohertz. Each switching event injects a small current transient through the parasitic capacitance between the digital switching network and the analog supply. Without the bypass capacitor, those transients produce millivolt-level spikes on VREF. Because the incremental ADC integrates its input over many clock cycles, even small VREF variations that are correlated with the conversion clock produce a systematic offset and gain error rather than random noise — so simply averaging more samples does not help. The practical effect is that an "8-bit" ADC may achieve only 6–7 bits of useful resolution without adequate reference decoupling.

ENOB is related to signal-to-noise-and-distortion ratio (SNDR) by:
`ENOB = (SNDR_dB − 1.76) / 6.02`

A 10 mV RMS noise floor on a 2.5 V reference span (assuming 0–2.5 V input range) adds ~12 dB of effective noise floor, reducing ENOB by two bits.

**Q2: PWM dimming exploits persistence of vision. What minimum PWM frequency avoids visible flicker, and how does that constrain the PWM clock divider?**

**Key concepts:** critical flicker fusion frequency, PWM clock calculation.

Human persistence of vision (the *critical flicker fusion frequency*) is approximately 50–60 Hz for steady, stationary sources, but rises to 100–160 Hz for peripheral vision or rapidly moving sources. For an LED used as an indicator in a lab setting, **≥ 100 Hz** is the commonly accepted minimum; consumer lighting standards (e.g., IEEE 1789) recommend ≥ 1 kHz to avoid biologically perceptible stroboscopic effects.

For an 8-bit PWM (256 counts per period):
`f_PWM = f_clock / 256`

To achieve f_PWM ≥ 100 Hz:
`f_clock ≥ 100 × 256 = 25,600 Hz`

At 24 MHz system clock, the first VC2 divider that exceeds this is any value ≤ 937:
`VC2 = 24 MHz / 8 = 3 MHz → f_PWM = 3 MHz / 256 ≈ 11,700 Hz` — well above the threshold.

Conversely, if VC2 were set too low (e.g., 24 MHz / 4096 ≈ 5,860 Hz → f_PWM ≈ 23 Hz), flicker would be plainly visible, especially when the eye scans past the LED.

### Exercise 3 — UART Telemetry

**Q1: The M8C lacks a hardware divider. What does `csprintf` cost in CPU cycles, and what would a fixed-format integer-to-ASCII routine save?**

**Key concepts:** software division, cycle counting, code size vs. speed tradeoff.

`csprintf` is a compact but general-purpose formatted-print function stored in PSoC Designer's ROM library. Formatting a single `%d` argument requires decimal conversion, which — without a hardware divide instruction — is implemented as repeated subtraction or a software long-division loop. A typical M8C software unsigned 8-bit `÷10` loop costs approximately 30–50 cycles per digit, and for three decimal digits plus the literal prefix `"ADC="` and suffix `"\r\n"`, the full `csprintf` call may execute **200–400 cycles** while consuming ~300 bytes of library code linked into Flash.

A hand-written `utoa3` function using the same repeated-subtraction strategy (see Section 4, reference firmware) processes all three digits in approximately **20–30 cycles** with no library overhead and uses only a few bytes of stack. This is roughly a **10× speedup** for this specific task.

At 9600 baud the bottleneck is the UART, not the CPU, so the difference is academic for this exercise. The tradeoff becomes critical when `csprintf` is called from within an ISR or when CPU load must be budgeted across multiple concurrent tasks at kHz rates.

**Q2: Why must the UART TX pin's drive mode be Strong, but the RX pin (if used) be High-Z digital?**

**Key concepts:** output drive modes, line contention, input thresholds.

The **TX pin** is driven by the UART digital block's output flip-flop. Configuring it as **Strong** (push-pull) means the PSoC actively drives the line high or low — the correct mode for a signal source. Using Open-Drain Lo would prevent the pin from driving the idle-high state (logic 1 between frames), causing the receiver to see a permanent break condition.

The **RX pin** receives signals from an external UART source (e.g., a USB-UART bridge). Configuring it as **Strong** would mean the PSoC is also *driving* that net — directly fighting the external driver, which risks drawing excessive current (potentially > 100 mA) that could latch up or damage either device. **High-Z digital** configures the pin's output buffer as a high-impedance input so that only the external source drives the signal, while the PSoC's Schmitt-trigger input comparator still interprets the logic level correctly.

This principle — outputs Strong, inputs High-Z — is the fundamental GPIO drive-mode rule for any CMOS digital interface.

### Exercise 4 — Waveform Generator

**Q1: The DAC6 has 6-bit resolution (64 levels). What is the theoretical SNR, and how is it affected by the chosen output filter cutoff?**

**Key concepts:** quantization noise, SNR formula for N-bit DAC, Nyquist bandwidth, filter roll-off.

For an ideal N-bit DAC with a full-scale sinusoidal output, the theoretical signal-to-quantization-noise ratio is:
```
SNR = 6.02 × N + 1.76 dB
```
For N = 6: **SNR ≈ 37.9 dB** (approximately 38 dB).

This assumes the quantization noise power is distributed uniformly over the frequency range from DC to half the DAC update rate (f_update / 2). If the DAC updates at 64,000 Hz (1 kHz output × 64 samples), the noise bandwidth is 0–32 kHz.

Adding a first-order RC low-pass filter with cutoff frequency f_c rolls off the noise above f_c. If f_c = 1 kHz (matched to the signal), the filter passes the signal with minimal attenuation while attenuating the out-of-band quantization noise by:
`noise reduction ≈ 10 × log10(f_update / (2 × f_c)) = 10 × log10(32) ≈ 15 dB`

This effectively increases the in-band SNR to approximately **38 + 15 = 53 dB** — equivalent to ~8.5 ENOB. This is the *noise-shaping* benefit of oversampling: using a DAC update rate higher than the Nyquist frequency of the signal and then filtering spreads quantization noise over a wider band, improving audible quality.

Choosing f_c too low (e.g., 200 Hz when generating a 1 kHz waveform) would attenuate the signal itself, reducing amplitude. Choosing f_c too high provides less noise rejection. The optimal cutoff is just above the highest signal frequency of interest.

**Q2: If you increased N (samples per period) to 256, what happens to ISR load? Is the M8C still capable of 1 kHz output? Show the math.**

**Key concepts:** ISR rate, CPU cycles available per ISR, percentage CPU load.

At N = 256 samples per period and f_out = 1 kHz:
```
ISR rate = 256 × 1000 = 256,000 ISR calls/second
```

At 24 MHz CPU clock, there are:
```
Cycles available per ISR = 24,000,000 / 256,000 = 93.75 cycles
```

A typical DAC-write ISR on the M8C (save context, read index, look up LUT, call `DAC6_WriteStall`, increment and mask index, restore context, `reti`) takes approximately **30–50 machine cycles** with optimized C code. At 93.75 cycles per ISR budget, this is **feasible** — but with very little margin.

CPU load:
```
Load = (ISR cycles used) / (cycles per ISR slot)
     = 50 / 93.75 ≈ 53 % CPU load
```

That leaves only ~47 % of cycles for `main()` tasks such as button polling and UART transmission. If `csprintf` is still used (200–400 cycles per call), it would preempt ISRs for several periods, causing visible waveform glitches at those moments.

**Conclusion:** 256 samples at 1 kHz is *technically* within the M8C's capability, but only with lean ISR code, no blocking calls in `main()`, and acceptance of ~53 % CPU load. Dropping to 500 Hz or reducing N to 128 provides comfortable margin. Demonstrate the calculation to receive full marks — a purely qualitative answer earns at most half credit.

## 7. Lab-Wide Discussion Question Answer Keys

**Q1: PSoC fabric vs. external op-amps — trade-offs in noise, bandwidth, drift, board area, and BOM.**

**Key concepts:** configurable analog, CMOS on-chip opamp limitations, BOM simplification.

PSoC 1's configurable analog fabric replaces discrete external op-amps, resistors, and capacitors with on-chip switched-capacitor circuits. The primary advantages are **dramatic BOM and board-area reduction**: a complete instrumentation amplifier + ADC stage that would require 5–10 discrete components plus a separate ADC IC is replaced by configuration in software at zero added component count. The configurable fabric also allows rapid design iteration — changing gain, filter topology, or ADC resolution is a firmware/configuration change rather than a board respins.

The trade-offs:

- **Bandwidth:** PSoC 1's CT opamp blocks have unity-gain bandwidths in the **1–4 MHz** range, compared with >10 MHz for quality discrete op-amps such as the TLV2460. For audio and sub-MHz signal conditioning the PSoC bandwidth is adequate; for high-speed RF or video signals it is not.
- **Noise:** On-chip CMOS op-amps typically exhibit **higher input-referred voltage noise** (several nV/√Hz floor) than precision bipolar op-amps (e.g., the OP27 at ~3 nV/√Hz). For low-noise sensor front-ends (thermocouple amplifiers, strain-gauge bridges) a discrete precision op-amp may be preferable as the first stage before digitization.
- **Drift:** SC blocks rely on capacitor ratios, which track well on-chip (±0.1 % across temperature) but are influenced by die temperature gradients. Discrete thin-film resistors on a quality substrate can achieve ±25 ppm/°C matching, better than on-chip.
- **Power:** A discrete precision op-amp can achieve sub-µA supply current; PSoC 1's on-chip blocks in high-power mode draw mA, which matters for battery-powered designs.

**Summary:** PSoC 1 wins on integration, flexibility, and BOM cost. Discrete components win on noise floor, bandwidth, drift, and ultra-low-power applications. The right answer often combines both: a discrete front-end stage followed by PSoC digitization and digital signal processing.

**Q2: Decoupling near PSoC 1 analog blocks — why more critical than a purely digital MCU?**

**Key concepts:** switched-capacitor transients, VREF sensitivity, supply rejection in SC circuits.

A purely digital MCU's supply current consists mainly of CMOS gate-switching transients (synchronous with the clock edge) and static leakage. These transients are broadband but predictable; a local 100 nF decoupling capacitor handles the charge demand. The supply-rejection requirement of digital logic is modest: even with 100 mV of supply ripple, a logic threshold in the middle of the rail provides adequate noise margin.

PSoC 1's analog blocks are far more sensitive because:

1. **SC blocks charge-transfer noise.** Each switched-capacitor clock cycle transfers a charge packet through the opamp feedback network. This appears as a current spike on VDD that, if not bypassed locally, couples through the power supply impedance into the opamp input — directly adding to the conversion result. The coupling is proportional to the supply impedance at the SC clock frequency (typically 100 kHz–2 MHz).

2. **VREF acts as an absolute reference.** Unlike a digital logic threshold, an ADC measures *volts relative to VREF*. A 5 mV ripple on a 2.5 V reference is a 0.2 % error — equivalent to losing 1–1.5 bits of ADC resolution. Removing the VREF bypass capacitor typically increases ADC output noise by 2–4 LSBs at 8-bit resolution, which students can observe directly by plotting ADC readings with and without the cap installed.

3. **Ground plane quality.** Switched-capacitor return currents must complete their loop through VSS. A high-impedance ground path (long thin jumper wire) adds millivolts of ground bounce that corrupt low-level analog signals. Star-grounding — running separate short returns from VSS, analog output pin, and VREF cap back to a common point — visibly reduces ADC noise on the oscilloscope.

**Q3: M8C vs. ARM Cortex-M — limitations and residual use cases for PSoC 1.**

**Key concepts:** ISA limitations, memory size, mixed-signal integration, legacy/cost.

The M8C's primary limitations relative to a Cortex-M0+ (e.g., as in PSoC 4):

- **No hardware multiplier or divider.** Software 8×8 multiply on the M8C takes ~20–50 cycles; a Cortex-M0+ has a single-cycle 32×32 multiply. DSP algorithms (FIR filters, PID controllers) that require frequent multiplications are costly.
- **Tiny memory.** 4 KB Flash and 256 B SRAM severely limit code complexity. A Cortex-M0+ PSoC 4 provides 32–128 KB Flash and 4–8 KB SRAM.
- **8-bit data path.** Variables wider than 8 bits require multi-instruction operations; 16-bit or 32-bit arithmetic is emulated in software.
- **24 MHz maximum clock.** A Cortex-M4 runs at 150–216 MHz; even a Cortex-M0+ at 48 MHz provides 2× throughput.

Scenarios where PSoC 1 is **still preferred:**

- **Extreme cost sensitivity.** The CY8C24223A in volume costs under $0.50. When the application requires only simple mixed-signal control (e.g., a simple thermostat, a battery fuel gauge), the PSoC 1 BOM is hard to beat.
- **Legacy designs.** Millions of existing PSoC 1 designs in the installed base require firmware updates, spare-part sourcing, and bug fixes without a hardware redesign.
- **Teaching tool.** The PSoC 1's simplicity — 256 B RAM, visible block architecture, 38-instruction ISA — makes it an ideal pedagogical platform for demonstrating mixed-signal microcontroller concepts without drowning students in peripheral complexity.
- **Very low power with analog.** In certain low-duty-cycle sensor applications, the PSoC 1 sleep current and analog block power gating can be competitive with simple Cortex-M0+ solutions, especially when the analog front-end would otherwise require separate ICs.

**Q4: ISSP vs. JTAG — mechanical and protocol differences, security implications.**

**Key concepts:** pin count, programming protocol, security fuses, glitch attack surface.

**Mechanically:**
ISSP (In-System Serial Programming) uses **5 wires**: VDD, VSS, XRES (reset), SDATA (bidirectional serial), and SCLK. JTAG uses **4 mandatory signals** (TCK, TMS, TDI, TDO) plus optional TRST, but is designed for daisy-chain boundary-scan across multiple devices on the same board. ISSP is a proprietary Cypress/Infineon protocol; JTAG (IEEE 1149.1) is an open standard.

**Protocol:**
ISSP operates in a "programming mode" entered by a specific voltage sequence on XRES and SDATA during power-up. Once in programming mode, Cypress-defined command vectors (bit streams) erase, write, and verify Flash in 64-byte blocks. The protocol is single-device point-to-point.

JTAG uses a state machine (TAP controller) navigated via TMS transitions. It provides access to both program memory (via flash-download instructions in the device's DR) and a full boundary-scan chain for board-level test.

**Security implications:**

- **Read-protect bits:** Both ISSP and JTAG support a *Flash Security* or *read-protect* configuration. On the CY8C24223A, setting the Flash security byte prevents ISSP from reading back program memory — a firmware protection measure. An attacker who can force the chip into programming mode (e.g., by glitching the power during the XRES sequence) may be able to bypass the security byte check and read the Flash regardless.
- **Glitch attack surface:** ISSP requires a precise timing window during power-up for programming-mode entry. Power or clock glitch attacks target this window to force the device into a known programming state with security checks bypassed. JTAG is vulnerable to similar attacks (inserting a glitch during the TAP reset or instruction register scan). Because JTAG provides boundary-scan access to every pin, a successful JTAG bypass potentially also gives an attacker the ability to probe or toggle arbitrary I/O.
- **Physical access requirement:** Both protocols require physical access to the programming pins. For production hardware, disabling the programming header (removing the connector, pouring conformal coating over the pads, or setting permanent lock bits) reduces the attack surface. PSoC 1's security model, like most 8-bit MCUs, is designed for *deterrence* rather than military-grade resistance; a sufficiently motivated attacker with a fault-injection setup can defeat it.

**Q5: Block budgeting — two strategies to fit the same functionality into 4 digital blocks.**

**Key concepts:** user module resource sharing, time-multiplexing, software emulation, Timer8 vs Timer16.

The conflict in Exercise 3 arises because Timer16 (2 blocks) + PWM8 (1 block) + UART TX8 (1 block) = **4 blocks**, exactly filling the budget. Adding a UART RX would overflow to 5. Two strategies to stay within 4 blocks:

**Strategy 1 — Downgrade Timer16 to Timer8.**
Replace the 2-block `Timer16` with a 1-block `Timer8`. The 8-bit period limits the count to 255, which constrains the achievable period before the interrupt. Compensate by either:
- Using a slower clock source (a higher VC divider) to maintain the same interrupt rate, or
- Implementing a *reload counter* in the ISR: count 4 ISR invocations before toggling the LED, effectively creating a 32-bit counter in software.
This frees one digital block for UART RX or another purpose.

**Strategy 2 — Software UART (bit-banging).**
Eliminate the UART user module entirely and implement TX in software: use the Timer8 interrupt to output one UART bit per invocation, manually toggling a Strong-mode GPIO. A 9600-baud bit cell is ~104 µs; a Timer8 interrupt at 9600 Hz handles start bit, 8 data bits, and stop bit sequentially, leaving all four digital blocks free for other modules. The cost is higher ISR code complexity and the inability to transmit and do other work simultaneously (the bit-bang ISR occupies the timer), but it is a legitimate solution that embedded engineers use in resource-constrained designs.

A third honorable mention: use **SPI** in place of UART (1 block for SIMO, hardware-assisted framing) if the host side supports SPI input. This is architecturally different from UART but often workable for short-cable lab benches.

**Q6: Drive modes — why so many, and a specific example of the wrong mode causing a functional bug.**

**Key concepts:** push-pull vs. open-drain, wired-OR, pull-up/pull-down, voltage collision.

Traditional MCUs offer two or three drive-mode options per pin. PSoC 1 exposes **eight** because its on-chip analog blocks require input pins to present no DC load (High-Z analog prevents the I/O buffer from biasing the analog column), and its reconfigurable fabric is used for protocols (I²C, 1-Wire) that require Open-Drain drive. Having a per-pin mode register makes it feasible to instantiate these protocols without external buffer ICs.

**Specific functional bug example — I²C with Strong drive mode:**

The I²C protocol requires that both SDA and SCL be **wired-OR** (open-drain) lines: multiple devices on the bus drive the lines low to assert a 0; the line returns to 1 only when *no device* is pulling it low. External or internal pull-up resistors provide the passive high state.

If a student accidentally configures the I²C SDA pin as **Strong** (push-pull):
- When the PSoC is transmitting a 0 (actively pulling SDA low), it also actively drives the line to 1 between bits. If a slave device holds SDA low during an ACK bit at the same moment, the PSoC's **Strong high** output fights the slave's low — creating a direct 5 V-to-GND current path through both output drivers. This can draw 30–100 mA continuously, overheating and damaging both the PSoC and the slave. Even if no damage occurs, the wire-OR arbitration is broken: the master never sees the slave's ACK because the master's own Strong output overrides the slave's attempt to pull the line low.

The correct mode for I²C is **Open-Drain Lo** (drive mode 5 in PSoC 1): the pin can actively pull low but cannot pull high. The external pull-up resistor passively restores the line when all drivers release it.

**Q7: Sampling theory in practice — DAC update rate and Nyquist compliance.**

**Key concepts:** Nyquist-Shannon theorem, DAC update rate, aliasing, output filter.

With N = 64 samples per waveform period and f_out = 1000 Hz, the DAC update rate is:
```
f_update = N × f_out = 64 × 1000 = 64,000 samples/second
```

The Nyquist theorem requires that the sampling (update) rate be at least twice the highest frequency component to be faithfully reproduced:
```
f_update ≥ 2 × f_highest
```
For the fundamental alone: `64,000 ≥ 2 × 1,000` → **satisfied with 32× oversampling margin.**

However, a 64-step staircase waveform contains harmonic content. The Fourier series of a sawtooth includes harmonics at 2×, 3×, … × f_fundamental. With N = 64 steps, the 32nd harmonic (32 × 1,000 = 32,000 Hz) is exactly at the Nyquist frequency of the DAC. Harmonics above f_update/2 **alias** back into the baseband as spurious low-frequency tones.

For a sine LUT (Exercise 4), harmonics above the fundamental are suppressed by construction (the LUT was computed with `sin()`), so aliasing is not a practical concern. For the sawtooth, harmonics above ~30 kHz alias to low frequencies. These alias products appear as additional "steps" or tones in the waveform if probed directly, but the recommended 1 kΩ + 100 nF output filter (f_c ≈ 1,600 Hz) attenuates all components above a few kHz, eliminating the aliased content before it reaches the speaker.

**Conclusion:** The DAC update rate satisfies Nyquist for the fundamental frequency at all settings (100 Hz through 1 kHz). Alias products from the sawtooth harmonics are real but audibly benign because they occur above the output filter's cutoff.
